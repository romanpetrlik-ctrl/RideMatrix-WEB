# Fare Settings

System Settings → Fare Settings contains separate Minimum fare rules and Fixed fares destinations, as well as an editable shared base distance-rate table, daily fare-surcharge settings, and explicit bank-holiday surcharge periods. Extras remains a future-configuration placeholder. Access remains limited to the existing System Settings role.

Minimum fare rules reference an active RideMatrix-managed Airport Fees record by its internal ID, never by a Google Places display label. Each rule stores a name or description, the managed location's internal ID, and an exact two-decimal GBP minimum base fare. It is associated whenever that location is the journey origin or destination; the other endpoint's distance and coordinates do not affect matching. The intended future base-fare behavior is `base fare = max(Distance Slabs fare, configured minimum base fare)`. Airport and POI fees remain separate charges, and dead mileage remains a separate calculation. New Booking applies them to the ride fare (see [New Booking](new-booking.md)).

The future minimum rule is displayed as `base fare = max(distance-slabs fare, configured minimum base fare)`. Airport fees remain separate and are not included. Fixed fares are directional origin → destination records; reverse direction requires a separate record. Each endpoint is identified either by a managed RideMatrix internal ID or by an explicit UK postcode criterion whose full-postcode or outward-code scope is retained. New Booking applies minimum rules to the ride fare; a fixed fare that matches a journey is shown as an unresolved line because its booking basis is not yet defined (see [New Booking](new-booking.md)).

Distance slabs are progressive GBP-per-mile bands shared by all vehicle categories. The first slab starts at 0 miles; bands are contiguous and start-inclusive/end-exclusive, and the final slab is open-ended. A journey charges each portion at the rate for that band. Distances and rates are parsed as decimal strings and calculated with integer arithmetic; only the final amount is rounded to the nearest penny, with exact half-pennies rounded up. The live test-distance display is an unsaved settings preview only, not a booking quote. No rates are seeded, and no passenger-fare calculation or vehicle-category uplift is connected.

Additional distance slabs (System Settings → Fare Settings → **Additional distance slabs**, a separate destination next to **Distance slabs**) are independent progressive slab sets stored in the same versioned configuration as `additionalDistanceSlabSets`: `{ id, name, target: { type: "airport" | "poi", id }, distanceSlabs[] }`. The landing page lists each saved set's name, linked airport/POI and slab summary with **Edit** and **Remove** actions (removal asks for confirmation) and a **Create additional distance slabs set** button. The create/edit page uses the same slab editor partial (`src/views/partials/distance-slab-editor.ejs`), client script and shared calculator as the base Distance slabs page, so the validation rules, open-ended final slab, and live **Test distance (miles)** preview are identical. **Copy base slabs data** replaces the editor rows with a snapshot of the saved base slabs (a server-rendered fallback works without JavaScript); the copy is independent, so editing it never changes the base slabs and later base edits never overwrite it. The required **Select POI or Place to link it** selector lists active Airport Fees airports and managed POIs by their configured names and stores only the internal RideMatrix ID. Each set links exactly one target, a target may be linked to only one set, and a missing or archived target is shown as an explicit error and never substituted. Earlier airport-specific sets (`airportDistanceSlabSets`, which could list several airports) are read as one additional set per linked airport with the same name and slabs; the first keeps its original ID. They are written under the new key on the next additional-set save, and history rows are untouched. Every save or removal appends an actor-attributed history version. Additional sets are **configuration only and are not yet used to price bookings**: there is no booking matching, pricing-table integration, fare calculation, or booking-total change.

Location-based discounts (System Settings → Fare Settings → **Location-based discounts**) are percentage discounts stored in the same versioned configuration as `locationDiscounts`: `{ id, name, location: { type: "airport" | "poi", id }, postcodePrecision: "full" | "outward", postcodes[], discountPercentage, startDate, endDate, enabled, discountBasis: "standard-distance-slabs-base-fare" }`. No rules are seeded, and new rules default to **Disabled**. The list page shows each rule's managed location, precision, postcode entries, percentage, validity, and status, with **Enable**/**Disable**, **Edit**, and **Remove** actions. Removal asks for confirmation first.

- **Location:** the location is an active Airport Fees airport or managed POI, stored by its internal RideMatrix ID only.
- **Postcodes:** postcode entries are separated by new lines, commas, or semicolons. They are normalized (case and spacing) and stored without duplicates for the precision the operator chose: **Full postcode** (`BH1 4RS`) or **Outward code** (`BH22`). An outward code intentionally covers its whole area.
- **Percentage:** must be greater than 0 and no more than 100, with up to 2 decimal places.
- **Dates:** optional inclusive `YYYY-MM-DD` dates. The end date cannot be before the start date.

The pure matcher `matchLocationDiscount` implements these semantics. It is called only through `resolveJourneyLocationDiscount` in `src/services/fare-calculation.ts` (see **Operational-base radius discounts** below), which applies radius precedence first; New Booking pricing uses it for the location-discount line.

- **Endpoints:** a rule matches only when one endpoint is the exact managed location ID and the other endpoint's structured (Google Places / selected address) postcode matches an entry at the selected precision. This works in either direction.
- **No guessing:** matching never uses display labels, free text, coordinates, the location's own postcode, proximity, or partial strings. A route passing through the area doesn't match.
- **Unresolved results:** a missing or invalid endpoint postcode, or more than one matching rule, returns `unresolved` instead of guessing or stacking.

The discount basis is the base fare from the standard Distance Slabs. Airport/POI fees, road charges, dead mileage, and other itemized fees are excluded, and Additional distance slabs are neither used nor changed.

To prevent stacking, a rule is rejected when another rule for the same location has an overlapping validity period and either:

- shares a postcode at the same precision, or
- covers or is covered by it through an outward code.

The error names the conflicting rule and entry. Disabled rules are included in this check, and **Enable** re-validates the rule, so a conflicting or unavailable rule can never be enabled. Each create, edit, enable, disable, or removal appends an actor-attributed history version. New Booking applies at most one location discount to the ride fare only (see [New Booking](new-booking.md)); existing bookings and customer charges are unchanged. The configuration key is optional (`?? []`), so no migration is required. An enabled, current operational-base radius discount for the same location takes exclusive precedence over these rules (see below).

## Operational-base radius discounts

**Operational-base radius discounts** (System Settings → Fare Settings, next to Location-based discounts) are stored in the same versioned configuration as `radiusLocationDiscounts`: `{ id, name, location: { type, id }, radiusMiles, discountPercentage, startDate, endDate, enabled, radiusCentre: "operational-base", discountBasis: "standard-distance-slabs-base-fare" }`. Nothing is seeded and new rules default to **Disabled**. The list, `/new`, `/:id/edit` and `/:id/remove` pages and the single POST (save, enable, disable, delete with `baseVersion`) follow the Location-based discounts pattern, require System Settings authorization and append actor-attributed history.

- **Location:** an active Airport Fees airport or managed POI, stored and matched by its internal RideMatrix ID only.
- **Radius:** greater than 0 miles, up to 3 decimal places, and no more than the dead-mileage maximum. It is measured as a straight-line (haversine) distance from the verified coordinates of the existing operational-base record, using the same Earth-radius convention as dead mileage. It is not road distance, postcode matching or route geometry. The boundary is inclusive (`distance ≤ radius`). No second base-coordinate setting is introduced and the dead-mileage free radius is separate and unchanged. Rules can't be saved or enabled while the operational base is unverified.
- **Percentage and dates:** the same rules as Location-based discounts (greater than 0 and no more than 100, with up to 2 decimals; optional inclusive dates with the end not before the start).
- **No overlaps:** two rules for the same location with overlapping validity periods are rejected with an error naming the existing rule. Disabled rules are included in this check, and **Enable** re-validates the rule.

`resolveJourneyLocationDiscount` (pure, `src/services/fare-calculation.ts`) resolves at most one discount per journey:

1. An enabled radius rule effective on the service date **governs its location exclusively**. If one endpoint is that exact managed location ID and the other endpoint's structured coordinates are within the radius, the radius discount applies, in either direction. Outside the radius, **no discount** applies. Postcode-scoped Location-based discounts for the same location are ignored, not used as a fallback, and never stacked. For example, with an active Heathrow radius rule, Dorchester–Heathrow receives no discount even if a Heathrow postcode rule covers `DT1`.
2. Postcode-scoped rules for other locations, and for locations without an enabled, current radius rule, behave exactly as before.
3. If coordinates are missing or invalid, the operational base is unverified, the service date is invalid, or more than one rule matches, the result is `unresolved` with a message. Nothing is guessed, chosen or stacked.

`calculateJourneyFare` calculates the standard Distance Slabs base fare and applies the resolved percentage to that base fare only, rounding half up to the penny. It then adds separately itemized charges unchanged: airport/POI fees, tolls, road charges, dead mileage and extras. Its `fareBreakdown` has a `base-fare` item, a `location-discount` item (rule ID, source, percentage, negative amount) and the separate charges. Its `snapshot` records the fare settings version, slabs, standard base fare, applied discount (rule, source, amount, radius, endpoint distance and operational-base reference), the precedence decision (governing radius rules and superseded postcode rules), charges and total. An unresolved discount returns no price.

**Booking prices.** New Booking (`src/services/booking-pricing.ts`, see [New Booking](new-booking.md)) supplies managed airport/POI IDs, structured coordinates and postcodes, and a routed passenger distance, and applies the same radius-over-postcode precedence. Bookings created before New Booking keep text-only stops, and the booking assignment page and customer charges are unchanged.

Dead miles fee settings have an **Active / Inactive** switch, a **Free radius (miles)** (default 10) and a **Rate per mile (£)**. The radius and rate are saved with an attributed Fare Settings history entry; postcode centroids are not used. Saving while the operational base is unverified is rejected.

The dead miles fee is calculated on booking pricing (`priceBooking`) when it is active. Distance is the straight-line (haversine) distance from the verified operational-base coordinates to whichever of the pick-up or drop-off is nearer. Chargeable miles are `max(0, nearest − free radius)` and the fee is `chargeable miles × rate per mile`, rounded to the penny and added as its own line. Within the radius the line is £0.00 (zero); when inactive it is not applicable. Free-text addresses without verified coordinates keep the price incomplete (no geocoding is performed).

**Current limitation:** free-text pick-up and drop-off addresses are not geocoded, so for them the dead miles fee stays unresolved and the price remains incomplete. Only stops with verified coordinates (for example managed airports and POIs) are priced.

Daily windows repeat each day and use operator-entered times and percentage. A start later than the end represents a window crossing midnight; the interval is start-inclusive and end-exclusive. Both surcharge types use `Europe/London` and are associated with the scheduled service/pick-up time, not booking creation time. Bank-holiday periods use explicit local dates and times, may span multiple days, and cannot overlap. No calendar or holiday-name inference is performed.

When an enabled bank-holiday period applies, its surcharge takes precedence over the recurring daily surcharge; the two are not combined. This precedence, time basis, time zone, and interval convention are stored in the configuration snapshots for future pricing integration.

Migration `0026_fare_settings` creates a disabled configuration with no assumed percentages or times. Migration `0027_fare_settings_distance_slabs` adds an empty slab list; migration `0028_fare_minimum_and_fixed_fares` adds empty rule lists to existing current configuration only. Migration `0032_minimum_fare_rules_without_radius` removes the obsolete per-rule radius from current minimum-fare records while preserving each rule's other fields and leaving append-only history untouched. These migrations do not add example rates or rewrite history. Saves update the current configuration and append actor-attributed snapshots to `fare_settings_history`; the history table rejects updates and deletes. Each Fare Settings page shows only the 3 most recent history versions (newest first); when more exist, **View all history** opens `/settings/fare-settings/history`, which lists every version newest first, 20 per page, with Previous/Next controls. Both views are limited and paginated in SQL; invalid `page` values show page 1 and out-of-range values show the last page. The history page requires the same System Settings authorization as Fare Settings. These forms are configuration only: the distance settings preview does not calculate booking fares, modify booking totals, or alter Toll & Fees behavior.

## Manual verification

1. As a superuser, open **System Settings → Fare Settings** and confirm **Minimum fare rules** and **Fixed fares** are separate destinations. Confirm Extras remains a future-configuration placeholder.
2. Open **Fare surcharge settings**, enable it, enter an operator-selected percentage and a window such as `23:00`–`06:00`, and save. Confirm the saved values and configuration-history version appear. Disable the rule and save; verify its saved values remain visible while the rule is disabled.
3. Open **Bank holiday fare settings**, enable the setting, and add two explicit periods. For example, enter 24 December 2026 18:00–27 December 2026 06:00 and 31 December 2026 18:00–2 January 2027 06:00 with operator-selected labels and percentages. Save, edit one period, remove the other, and save again.
4. Try an invalid calendar date, an end before its start, and overlapping periods; each should be rejected with a visible error. Confirm the page explains bank-holiday precedence over the recurring surcharge.
5. On **Distance slabs**, enter `0`–`10` at `3.00` and `10`–open-ended at `2.70`; set the test distance to `12` and `12.4` and confirm previews of `£35.40` and `£36.48`. Edit a rate without saving and verify the preview updates immediately. Add, remove, and save slabs, then confirm saved rows and configuration history.
6. Try a non-zero first start, a gap, an overlap, a missing final end, an interior open end, a negative/malformed value, and an empty rate; each should be rejected with a field-level error. Confirm the last slab is marked open-ended.
7. On **Minimum fare rules**, add a rule for a managed airport or POI with a £25 minimum. Confirm there is no per-rule radius field, and that the form identifies the location by its RideMatrix internal ID. Verify a journey matches when that ID is either endpoint even if the other endpoint is far away; the displayed future formula uses only the base fare, and airport/POI fees stay separate. Edit the rule and confirm its name, internal ID, and minimum amount remain saved.
8. On **Fixed fares**, create a directional fare between a managed POI and a full-postcode or outward-code criterion. Confirm the RideMatrix ID, direction, postcode scope, and exact GBP amount are retained; edit and remove records and confirm each change increments configuration history.
9. On a booking assignment screen, confirm there are no dead-mileage flags. Create a booking with a pick-up 17 miles from the verified operational base and a drop-off beyond it; with **Dead miles fee** active at radius 10 and rate £1.00, the **Dead miles fee** line must read £7.00.
10. On **Dead mileage settings**, switch between Active and Inactive, set the **Free radius (miles)** (default 10) and **Rate per mile (£)**, and save. Try zero or negative radii, a malformed rate, and an over-maximum radius; confirm each is rejected. Without a verified operational point, confirm the form is unavailable and server-side saving is rejected. This setting does not affect Minimum Fare Rules matching.
11. The unit tests in `booking-pricing.test.ts` cover the fee: inactive, nearer endpoint choice, the £7.00 example, zero inside the radius, and unresolved coordinates.
12. Confirm airport fees and minimum-fare behavior remain unchanged; no payment is processed.
13. On **Additional distance slabs**, select **Create additional distance slabs set**. Enter a name, choose an airport or POI under **Select POI or Place to link it**, and select **Copy base slabs data**; confirm every base row, including the open-ended final slab, is copied. Change a rate and set **Test distance (miles)** to `12`; confirm the preview updates immediately and shows an incomplete state when a gap is introduced. Save, confirm the set is listed with its linked target and slab summary, reopen it with **Edit** and confirm the values, then open **Distance slabs** and confirm the base rates are unchanged. Try linking the same target to a second set and confirm rejection; remove a set and confirm the confirmation page appears first.
14. On **Location-based discounts**, select **Create location-based discount**. Confirm the matching-semantics notes and the "Configuration only" note are shown and the status defaults to **Disabled**. Choose an airport, select **Outward code**, enter `bh22`, enter `10`, and save. Confirm the list shows `BH22` and **Disabled**. Create a second rule for the same airport with **Full postcode** `BH22 8AB`, and confirm it is rejected with an error naming the first rule and `BH22`. Enter an invalid postcode (`BH1 4R`), `101`, or an end date before the start date, and confirm the field errors keep your values. Enable, then disable, the saved rule. Edit it and add dates. Remove it after confirming. Check that **Configuration history** records each change, and that Distance slabs, Additional distance slabs, Minimum fare rules, Airport Fees, POI fees, and New Booking prices are unchanged.
15. On **Operational-base radius discounts**, confirm the page shows the verified operational-base coordinates, the "Not yet applied to booking prices" note and the precedence notes. Select **Create operational-base radius discount**, choose an airport, and enter radius `10` and `15`%. Confirm the status defaults to **Disabled**, then save. Try `0` or `1.2345` miles, `101`%, an end date before the start date, or a second rule for the same airport with overlapping dates, and confirm each is rejected with a clear error and your values kept. Enable, disable, edit and remove the rule, and confirm each change appears in **Configuration history**. Confirm **Dead mileage settings** still shows the same free radius.
16. Pricing behaviour is verified by `src/services/fare-calculation.test.ts` (`npx tsx --test src/services/fare-calculation.test.ts`). It covers exact-ID matching, both directions, the inclusive boundary, Dorchester–Heathrow without a discount, no stacking, postcode fallback, unresolved coordinates, and unchanged fees.

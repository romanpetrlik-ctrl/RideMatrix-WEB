# Fare Settings

System Settings → Fare Settings contains separate Minimum fare rules and Fixed fares destinations, as well as an editable shared base distance-rate table, daily fare-surcharge settings, and explicit bank-holiday surcharge periods. Extras remains a future-configuration placeholder. Access remains limited to the existing System Settings role.

Minimum fare rules reference an active RideMatrix-managed Airport Fees record by its internal ID, never by a Google Places display label. Rules store a named description, positive radius in miles, and exact two-decimal GBP minimum base fare. For a journey to the airport, radius matching uses the configured drop-off operational point; for a journey from the airport, it uses the configured pick-up operational point. The other endpoint must have usable coordinates within the inclusive straight-line/geodesic radius; road distance and postcode centroids are not used. Five miles is 8,046.72 metres. A location without valid configured operational coordinates cannot be used to create a minimum rule.

The future minimum rule is displayed as `base fare = max(distance-slabs fare, configured minimum base fare)`. Airport fees remain separate and are not included. Fixed fares are directional origin → destination records; reverse direction requires a separate record. Each endpoint is identified either by a managed RideMatrix internal ID or by an explicit UK postcode criterion whose full-postcode or outward-code scope is retained. Neither rule type is connected to booking-price calculations.

Distance slabs are progressive GBP-per-mile bands shared by all vehicle categories. The first slab starts at 0 miles; bands are contiguous and start-inclusive/end-exclusive, and the final slab is open-ended. A journey charges each portion at the rate for that band. Distances and rates are parsed as decimal strings and calculated with integer arithmetic; only the final amount is rounded to the nearest penny, with exact half-pennies rounded up. The live test-distance display is an unsaved settings preview only, not a booking quote. No rates are seeded, and no booking-price calculation or vehicle-category uplift is connected.

Daily windows repeat each day and use operator-entered times and percentage. A start later than the end represents a window crossing midnight; the interval is start-inclusive and end-exclusive. Both surcharge types use `Europe/London` and are associated with the scheduled service/pick-up time, not booking creation time. Bank-holiday periods use explicit local dates and times, may span multiple days, and cannot overlap. No calendar or holiday-name inference is performed.

When an enabled bank-holiday period applies, its surcharge takes precedence over the recurring daily surcharge; the two are not combined. This precedence, time basis, time zone, and interval convention are stored in the configuration snapshots for future pricing integration.

Migration `0026_fare_settings` creates a disabled configuration with no assumed percentages or times. Migration `0027_fare_settings_distance_slabs` adds an empty slab list; migration `0028_fare_minimum_and_fixed_fares` adds empty rule lists to existing current configuration only. Neither migration adds example rates or rewrites history. Saves update the current configuration and append actor-attributed snapshots to `fare_settings_history`; the history table rejects updates and deletes. These forms are configuration only: the distance settings preview does not calculate booking fares, modify booking totals, or alter Toll & Fees behavior.

## Manual verification

1. As a superuser, open **System Settings → Fare Settings** and confirm **Minimum fare rules** and **Fixed fares** are separate destinations. Confirm Extras remains a future-configuration placeholder.
2. Open **Fare surcharge settings**, enable it, enter an operator-selected percentage and a window such as `23:00`–`06:00`, and save. Confirm the saved values and configuration-history version appear. Disable the rule and save; verify its saved values remain visible while the rule is disabled.
3. Open **Bank holiday fare settings**, enable the setting, and add two explicit periods. For example, enter 24 December 2026 18:00–27 December 2026 06:00 and 31 December 2026 18:00–2 January 2027 06:00 with operator-selected labels and percentages. Save, edit one period, remove the other, and save again.
4. Try an invalid calendar date, an end before its start, and overlapping periods; each should be rejected with a visible error. Confirm the page explains bank-holiday precedence over the recurring surcharge.
5. On **Distance slabs**, enter `0`–`10` at `3.00` and `10`–open-ended at `2.70`; set the test distance to `12` and `12.4` and confirm previews of `£35.40` and `£36.48`. Edit a rate without saving and verify the preview updates immediately. Add, remove, and save slabs, then confirm saved rows and configuration history.
6. Try a non-zero first start, a gap, an overlap, a missing final end, an interior open end, a negative/malformed value, and an empty rate; each should be rejected with a field-level error. Confirm the last slab is marked open-ended.
7. On **Minimum fare rules**, add a rule for a managed airport with a 5-mile radius and a £25 minimum. Confirm both direction-specific operational points are described, the formula uses only base fare, and airport fees stay separate. Try a missing/invalid operational point and verify that saving fails with a field-level explanation.
8. On **Fixed fares**, create a directional fare between a managed POI and a full-postcode or outward-code criterion. Confirm the RideMatrix ID, direction, postcode scope, and exact GBP amount are retained; edit and remove records and confirm each change increments configuration history.
9. Confirm no fare calculation or booking-total behavior is present or changed.

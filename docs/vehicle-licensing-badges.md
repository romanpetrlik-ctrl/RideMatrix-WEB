# Vehicle licences and badge snapshots

Vehicle licence records remain in `vehicle_licensing_authorities`, preserving the existing many-licences/many-authorities model. `license_type` distinguishes Hackney Carriage from Private Hire, and `vehicle_license_badge` belongs to that exact authority-specific licence. Neither value is the vehicle class, licensing authority, licence reference, nor a driver badge. Older records remain readable with an unset type and badge; they are not assigned an inferred type.

Vehicle managers create and edit these fields on the vehicle detail page. A blank badge on an edit preserves its existing value; the explicit “Clear current Vehicle licence badge” checkbox clears it. Licence validity remains sourced from `valid_from` and `valid_until`.

Vehicle documents continue to use the existing `vehicle_documents.content` PostgreSQL `BYTEA` backend. There is no external object-storage integration: `storage_key` is not used and files are not placed in a public static directory. Uploads retain server-side extension, MIME, signature, and size checks; store byte size and a SHA-256 checksum for new uploads; and are associated with a vehicle licence when selected. Legacy document rows are backfilled with byte size when content is present; their checksum remains unavailable rather than being represented with a different hash algorithm. Replacements are scoped to the same vehicle, document type, and licence, and retain prior versions with `is_latest = FALSE` and `superseded_at`. Historical and current documents remain available only through the authorized, no-store, rate-limited document route. The document's expiry display is read from `expires_on`, not from its filename.

The existing booking assignment service accepts an explicit `vehicleLicenseType`. When supplied, it selects compatible authorities using an active vehicle licence of that type and snapshots that licence's badge (or `NULL` when missing) to `customer_bookings` and `booking_assignment_audit`. Reassignment overwrites only the current booking snapshot; changes to vehicle licence data do not rewrite prior booking snapshots. `unassignBookingVehicle` clears the current vehicle/type/badge and records the unassignment while leaving the prior assignment audit intact.

There is currently no booking assignment route or assignment form in this repository: the booking pages are customer-history views. Consequently, no existing form supplies Hackney/Private Hire context or invokes the assignment service. The service and booking display are prepared to carry the explicit context and snapshot, but wiring a new booking workflow requires a product decision about where users choose that context. No licence type is guessed when that context is absent.

## Follow-up to merged PR #131: assignment workflow blocker

Inspection of `main` after [PR #131](https://github.com/romanpetrlik-ctrl/RideMatrix-WEB/pull/131) identified the customer booking-history area as a possible management destination. Its existing authorization requires the exact `admin` role (`requireAdminSession` in `src/routes/customers.ts`); no new dispatch role or broader access is justified. However, the operator identity/licence source used by assignment is not connected to the operator onboarding source:

- Setup creates an identified operator in `operators`, links it through `system_setup_state.operator_id`, and saves its PHO licence in `operator_licences` (`saveOperatorLicence` in `src/services/system-setup.ts`).
- `resolveCompatibleLicensingAuthorities` in `src/services/licensing.ts` instead reads `operator_licensing_authorities`. Setup does not populate that table, and no existing synchronization or mapping connects its licence rows to `operator_licences`.
- The legacy `operator_licensing_authorities.operator_id`, `customer_bookings.operator_id`, and audit operator IDs are unconstrained text, not foreign keys to `operators`. The foundation integration test explicitly preserves that schema. A legacy ID is therefore not evidence of a verified operator identity, and the assignment service does not check the operator registry.

The registry can identify the setup operator, but it cannot establish which legacy assignment licence records belong to that operator. Selecting the setup operator alone does not make its PHO licence visible to the existing assignment service. Selecting arbitrary legacy IDs instead would not establish a reliable named operator. This follow-up stops before adding an assignment form or changing licensing policy; it does not duplicate licence records, reinterpret PHO as the vehicle licence type, or modify production data.

### Decisions needed to unblock implementation

1. Confirm the canonical operator/licence source for dispatch: should assignment consume `operator_licences`, or should an explicit, audited mapping connect setup records to `operator_licensing_authorities`? Specify how existing legacy IDs are reconciled and how licence status, validity, changes, and revocation remain consistent without a competing source of truth.
2. Confirm whether dispatch uses the single setup operator or an explicitly selected registered operator, and which operator states are assignable. Do not infer this from the separate vehicle Hackney Carriage / Private Hire context.
3. Confirm whether imported historical bookings are read-only or can be promoted into operational bookings. Customer history currently combines `customer_bookings` and `imported_bookings` (`loadBookings` and `listRecentBookingsForCustomer` in `src/services/customers.ts`). Cabcher import writes `imported_bookings`; assignment and its audit only target `customer_bookings`. No existing promotion/link exists. Do not copy an imported history row into a second, conflicting booking or offer it an assignment action without that decision.

Once the operator mapping is defined, the smallest workflow can live in the existing admin-only customer booking area and target only verified operational booking IDs. It must use the existing CSRF, no-store, validation, and rate-limit conventions; derive the actor from the authenticated session; and accept only operator, driver, vehicle, and explicit vehicle licence type as assignment inputs. Client-supplied badge, authority, actor, and service-date overrides must not control the saved snapshot.

Server-side saves must call `assignBookingWithLicensing` using the stored booking service date, resolve an active compatible licence of the selected type, and commit the booking snapshot and audit together. Reloaded forms and history must show the saved type and badge, including an explicit unset warning for a missing badge. Reassignment and `unassignBookingVehicle` must retain earlier audit snapshots. The requested route-level integration coverage (both types, persistence/display, missing badge, rejected assignments without partial writes, reassignment/unassignment, audit history, authorization, CSRF, and tampering) remains pending until this blocker is resolved; existing service tests are not a substitute for that end-to-end coverage.
